## 二、DTR 极性可切换（已实现）

### 1. 语义

默认极性是"未断言 = 高、断言 = 低"（标准 TTL 低有效）。有些目标板的 BOOT/EN 是**高有效**，
需要把 PA3 这一路整条反过来：

| DTR 极性 | 未断言 / 未配对 / 断链 | 上位机断言 DTR | 适用 |
|---|---|---|---|
| `0` 默认（出厂） | **高** | **低** | BOOT0 / EN 低有效 |
| `1` 反相 | **低** | **高** | BOOT / EN 高有效，或中间有反相管 |

**只翻 DTR/PA3**：RTS/PA2 的复位脉冲（`RTS_PULSE_*`）与 `0x7F` 一键下载时序都不受影响 ——
那两条是"低 = 复位 / BOOT0 拉高 = 进 Bootloader"的固定语义。

### 2. 两条载体（效果完全一样）

| 载体 | 用法 | 限制 |
|---|---|---|
| ① 下行魔数 `A5 5A 01 <pol>` | 任何串口工具/面板：**HEX 发送**、关掉"发送新行"、**一次性发这 4 字节**；主机在 `USB_RxQuery()` 里就地吃掉，**不发往目标设备** | 被 USB 读取边界切开且之后没有后续数据时认不出来（那 4 字节会当普通数据透传）→ 重发一次即可 |
| ② 厂商请求 `0xA3`（`wValueL.bit0`） | 自研上位机：`bmRequestType=0x40, bRequest=0xA3, wIndex=0, wLength=0` | 本项目扩展的请求码，标准驱动永不发送（零误触发）；但 ch341 驱动占着设备时用户态**发不出任意厂商请求**，需 libusb 独占（Linux 先解绑 `ch341`） |

链路层：`OPCODE_DTR_POL = 0x02`（`PKT_CMD_RSP_STATUS` 应答里，载荷 1 字节）。
主机收到魔数/0xA3 后置 `gDtrPolPending`，由 `rf_uart_rx.c` 组包下发（缓存一份，丢包会随同序号重发；
从机对"极性没变"幂等，不会重复擦 Flash）。

### 3. 从机实现要点

- **ISR 只记值**（`rfQueueDtrPol`）→ 主循环 `rfFlushDtrRts()` → `rfApplyDtrPol()`：立刻改 PA3 电平 +
  写 Flash。**不在射频中断里擦 Flash**（擦一个扇区几毫秒）。
- **掉电保存**在绑定信息扇区（`0x3B000`）：`rfBoundInfo_t` 新增 `dtrPol` + `dtrPolChk`（互补校验，
  老固件记录读到 `0xFF` 自动判为默认极性）。**四条 Flash 写路径统一由 `rfSaveBoundInfo()` 补这两个
  字段** —— 记录是整个扇区重写的，任何写点漏填都会把栈垃圾写进 Flash（VERIFY 还会失败）。
- `UART_Init()` 先 `RF_DtrPolLoad()` 再按极性决定 PA3 的**上电默认电平**（反相时上电即低，
  不会先高一下再低）。
- 主机侧**不保存**极性：指令是绝对值、owner 是从机，所以主机上电/换主机不会把设定冲回去。

### 4. 已知边界与坑

- 魔数请**单独、一次性**发（见上表①）；`tools/loss-test/dtr_pol_test.py --mode status` 会打印两条
  载体的准确字节，`--mode check`（从机侧 PA0↔PA1 短接）可验"魔数被吃掉 + 其余字节透明"。
- 上位机开端口通常**会自动断言 DTR/RTS**（驱动行为）：默认极性下 = PA3 拉低；若 PA3 接目标 BOOT0，
  会把它按进 Bootloader。不想动目标就把工具的 DTR/RTS 勾掉。
- **降级会丢设定**：老固件（无此功能）重写配置扇区时只写 8 字节记录，会把 `dtrPol` 一起擦掉。
  别用「全片擦除」烧写（会清掉整个配置扇区：极性 + 绑定信息）。

### 5. 过滤器单元测试结论

魔数过滤器（`usb_uart.c` 的 `dtrPolMagicFilter()`）把源码函数原样抽出来单独编了测试：
**穷举 `5^9` 个 9 字节串 + 3000 组随机流**，判据 = 逐字节与模型一致 + 无越界写 + 收尾不扣字节 → 全通过。

> 测试抓出的一个真问题（已修，**别改回去**）：原设计"结尾的半截前缀一律暂存到下一包"会让
> `A5` / `A5 5A` 这类结尾被**无限期扣住** —— 对目标设备就是"迟到 + 乱序"，比"指令没认出来"糟糕得多。
> 现在只有 `keepTail`（环里确实还有待处理数据）才暂存，否则原样吐回；语义注释在函数尾部。

## 三、断连重连：现状与已排除项

### 1. 现场与关键判据

- 近距离连上 → 走远直到断开 → 走回 10cm 内 → **仍连不上；只有重启主机能回连**。
- **"重启主机就好"是决定性判据**：只有上电那条射频初始化路（`RFRole_BasicInit` → `RFEND_DevInit` +
  `RFIP_RegInit` + 唤醒寄存器 + 前端校准）能把接收救回来；`RFIP_SetRx()` 不会补这一段。

### 2. 已确认 / 已排除

- **从机侧没问题**：从机 `rf_disconnect()` 全工程**不碰射频**（既不 `Stop` 也不 `Shut`），断连后回落
  广播，它的回连一直正常 → 问题在**主机**。
- 上一轮方案 `RF_DISCONNECT_SHUT = 0`（断连只 `RFRole_Stop()`、不关电源）**实测不够**，仍需重启。

### 3. 本轮新增的四档 A/B（`rf_uart_rx.c` 顶部，默认仍为 0）

| 值 | 断连时怎么做 | 依据 / 假设 |
|---|---|---|
| `0`（默认） | `RFRole_Stop()` | 上一轮 WIP，**实测不行** |
| `1` | `RFRole_Shut()` + `rfRadioRecover()`（唤醒 + 校准） | 最早的老行为 + 补上恢复 |
| `2` | **什么都不做**（只复位参数与标志） | 对齐从机做法 —— 从机就是这么干的，且它回连正常 |
| `3` | `RFRole_Stop()` + `rfRadioHardReInit()`（复刻上电那条路） | **最接近"重启主机"**，建议优先试 |

另外：`rf_disconnect()` 里 `gIntervalTimer = 0` → 断连后按**未配对方式连续收包**（上电时该值初值就是 0，
`timeOut = 0` 表示"不超时"），不再沿用连接期的 10 ms 窗口。

> ⚠️ **`RFRole_Init()` 的坑（务必知道）**：它结尾执行 `pCbs = NULL`（见 `rf.c`），清掉的正是
> `RFRole_RegisterStatusCbs()` 注册的**应用回调** → 运行时重建射频后**必须重新注册**，否则射频"在收"
> 但没人处理包，现象与"聋了"一模一样。`rfRadioHardReInit()` 里已补并有注释。

## 六、代码侧两个未决点的复核结论（2026-10-15 追加）

> 对应上面 §四 的第 5、6 条。**只做了复核与实测，没有改任何功能代码。**

### 1. 从机把 CRC 错误当超时处理 —— 结论：**安全，且方向正确；但有一处语义耦合值得记录**

**证据链**

- `rfStatusCBs_t` 第三项确为 `pfnRfRxCrcCB_t pfnCrcErrCB`（`APP/include/rf.h`）。从机 `rfCBs` 填的是 `rfProcessTimeout`（`rf_uart_tx.c:66`），主机填的是自己的 `rfProcessCrcError`（`rf_uart_rx.c:149`）。
- **从机是轮询发起方**：一次 CRC 错误 ≡ 一次"没收到应答"，落到 `rfProcessTimeout` 恰好得到**重传**（`STA_BUSY → STA_RESEND`、`resendCount` 重置）——这正是发起方该做的动作。
- **主机是应答方**：它只需继续听，所以 `rfProcessCrcError()` 刻意只置 `WAIT` + 计数，**不重传、不计入 `gTimeout`**。
- ⇒ **两端不对称是架构决定的，不是缺陷。**

**关键：从机没有复现主机那个"CRC 之后永久变聋"的坑。**
从机的接收窗口是一次性的（`RFIP_SetRx`），而重开窗口有两条可靠路径：`rfProcessTx()` 每次（重）发完都 `rf_rx_start(150)`；`rfProcessRx()` 的 seq 失步分支也 `rf_rx_start(150)`（该分支注释已专门写明"不重开会永久停摆"）。
链路是闭合的：CRC 错误 → `STA_RESEND` → `RF_StatusQuery()` 重发 → `rfProcessTx()` 重开窗口。**不会卡死。**

**唯一耦合（建议补注释，暂不改码）**：当 CRC 错误到达时若 `gRfStatus != RF_STATUS_WAITRSP`（典型是重传后的 `REWAIT`），会走 `else` 分支 `++gTimeout` —— 即**持续干扰会被计入断开门槛**，最终 `rf_disconnect()` 回落广播。
看着是有意的（干扰重就更快回落广播重配），代价是"干扰重"与"真断开"在语义上被合并了。
若日后想让 CRC 只触发重传、不老化链路：新增 `rfProcessCrcError()`，只做 `STA_BUSY → STA_RESEND`，**不碰 `gTimeout`**。**留待台架判读是否需要。**

### 2. 从机 RAM 余量 —— 结论：**760 B 不是"余量"，它就是整条栈；开日志要吃掉 42%**

精确拆解（`RF_Uart/build/RF_Uart.map` + `objdump -h`；RAM = 12 KB = 12288 B）：

| 区域 | 大小 | 占比 | 备注 |
|---|---|---|---|
| `.highcode`（代码放 RAM） | **7120 B** | 58.0% | 最大单项 |
| `.data` | 16 B | 0.1% | |
| `.bss` | 4392 B | 35.7% | |
| **栈**（`.stack` 长度=0，`_eusrstack`=0x20003000） | **760 B** | **6.2%** | 从 `_end`(0x20002d08) 到 RAM 顶 |

- **`.highcode` 明细**：RF 协议栈 2718 B（`rf_ip` 1582 + `rf_basic` 1136）、应用 2716 B（`rf_uart_tx` 1496 / `uart` 702 / `buf` 294 / `rf` 218 / `main` 8）、`CH57x_sys` 752 B（含 `SetSysClock` 576）、ISP 库 788 B、启动 144 B。
- **`.bss` 明细**：`uart_buf` **3072 B（占 `.bss` 的 70%）**、`rf_buf` 512、`gTxBuf` 264、`RxBuf` 264。

**要点**

1. `.stack` 段长度是 **0** → 栈直接从 RAM 顶向下长，**没有保留区、没有溢出检测/金丝雀**。760 B 就是"主循环 + ISR 嵌套 + Flash 操作"的全部栈预算。
2. 用 `-fstack-usage` 实测：**无 dynamic 帧**（没有 VLA/alloca），静态分析有效；应用层最大帧仅 48 B（`rfProcessRx`），printf 那些大帧（`number` 128 / `log_vsprintf` 96）**已被 `--gc-sections` 全部丢弃**。
3. ⚠️ **从机当前根本没有运行时日志**：`-DDEBUG` 只加在主机（`RF_UartDongle/CMakeLists.txt:95`），从机的 `PRINT` 展开为**空**（`CH57x_common.h` 的 `#ifdef DEBUG … #else #define PRINT(X...)`）。已用固件字符串反查确认：从机 ELF 里**没有任何 `PRINT` 文案**（"resend fail" 等一个都没有），主机里全在。
4. ⚠️ **开 `-DDEBUG` 的实测代价**（本机实际编译）：

   | | 不开（现状） | 开 `-DDEBUG` | 增量 |
   |---|---|---|---|
   | FLASH | 13024 B / 5.30% | **18816 B / 7.66%** | +5792 B |
   | RAM | 11528 B / 93.82% | **11844 B / 96.39%** | +316 B（`.highcode` +184、`.data` +108、`.bss` +24） |
   | **栈预算** | **760 B** | **444 B** | **−316 B（−42%）** |

   同时会把 newlib-nano 的整套 stdio（`findfp` / `makebuf` / `malloc` / 锁 …）链进来。
   ⇒ **这就是"从机不能随手加日志"的硬数据**：想在从机侧区分 CRC 错误与超时，代价是 42% 的栈预算。
5. 若日后真要在从机加功能：**最大单笔杠杆是 `uart_buf`（3072 B）**；其次是确认 `.highcode` 里是否全部真的必须跑在 RAM。
6. `my_printf.c` 在从机被 100% 丢弃（其函数全在 "Discarded input sections" 里），属**死源码**——可考虑从从机源列表移除（不省 RAM，只是清爽）。

### 3. 小结

| 未决点 | 结论 | 建议 |

## 七、★ 断连重连根因已定位并修复（2026-10-15 追加，推翻 §三 的射频假设）

> **结论：回连不上与射频无关，是主机把从机"永久 reject"了。** §三 的"射频变聋"假设**不成立**——
> 那四档 A/B（`RF_DISCONNECT_SHUT` 0/1/2/3）是在修一个不存在的故障。修复已实现并编译通过，**待台架验证**。

### 1. 怎么拿到的证据

主机日志在 **WSL 的 `/dev/ttyACM0`**（USB 走 usbip 转发进 WSL；WSL 里 `acm` 驱动已建 `/sys/class/tty/ttyACM0`，
但 `/dev` 节点不存在，普通用户 `mknod` 无权限 → 用 **SeaHi Serial 的 WSL 分栏**选 `/dev/ttyACM0` 读，
或走 MCP：`serial_select_port{pane:"wsl",port:"/dev/ttyACM0"}` → `serial_get_output{pane:"wsl"}`。

现场日志（贴合后仍是 `rssi -27`，射频完全正常）：

```
[15:24:15.428] disconnect.
[15:24:15.428] cfgVal=10
[15:24:15.428] bound rsp sent.6EDD28B6 4a      ← 主机接受了，生成了新身份 dd28
[15:24:16.277] rej 78   local dd28 remote a2a2 rssi -79
[15:24:25.276] rej 1234 local dd28 remote a2a2 rssi -61
[15:27:17.304] rej 1946 local dd28 remote a2a2 rssi -27   ← 贴脸了也照拒
```

并且：**全 3691 行日志里一次 `bound success (link up).` 都没有**；`crc/rxerr` 正常、RSSI 连续可读
（−79 一路走到 −22）——**射频根本没聋，是主机在拒收**。

### 2. 根因：一个"从未被确认、也从未落盘"的绑定提议覆盖了已达成一致的绑定值

`rf_uart_rx.c` 的 `rfProcessRx()`（`BOUND_STATUS_IDLE` 分支）里，接受绑定请求时**无条件**换身份：

```c
if( reg )
{
    gDataSeq = 0;
    gServerData = rf_rand16( rssi );      /* ★ 连"回连"路径也换，且新身份只靠一包可能丢的 RSP 传递 */
    ...
    pRsp_t->severData = gServerData;
    rf_tx_start( pPkt_t, 20 );
}
```

而**落盘在另一处** —— `rfBoundConfirm()`，只在"从机用新参数发来第一包"时才调用：

```c
static void rfBoundConfirm( void ) { RF_bound_Flag = 1; PRINT("bound success (link up).\n"); rfSaveServerData(); }
```

失败链条（每一步都有上面的日志对应）：

| 步 | 主机 | 从机 |
|---|---|---|
| ① 拉距断连 | `rf_disconnect()` → IDLE，`gServerData` 仍 = **a2a2**（与从机一致） | 回落广播 `BOUND_REQ(severData=a2a2)` |
| ② 边缘偶然收到一包（RSSI **−79**） | 匹配 a2a2 → 接受 → **`gServerData` 立刻变成 `dd28`**，发出 `BOUND_RSP` | 等 RSP |
| ③ **RSP 丢了**（边缘必丢） | `rfBoundConfirm()` **永不调用** → dd28 **从未落盘** | **没收到** → 仍广播 a2a2 |
| ④ 超时 | `rf_disconnect()` → IDLE，**`gServerData` 仍是 dd28** | 仍 a2a2 |
| ⑤ 之后 | 拿 dd28 比对 a2a2 → **永久 reject**（RSSI 回到 −27 也照拒） | 一直广播 a2a2 |

**本质**：主机把"一个尚未被对端确认的提议值"当成了"已生效的绑定值"，提议失败后从不回滚
（`rf_disconnect()` 刻意保留 `gServerData`——那本意是对的，但它保留的是一个跑偏的值）。

### 3. 为什么"重启主机"能连上（关键判据的解释）

重启**不是修复了射频，而是把 RAM 里跑偏的身份回滚成 Flash 里双方一致的那个值**：

`RF_UartRxInit()` → `rfLoadServerData()` → `gServerData = pInfo->serverData`（`BOUND_INFO_FLASH_ADDR = 1024*236`）。
而 `rfSaveServerData()` **只在 `rfBoundConfirm()` 里调用过**，即最后一次**真正建链成功**那一刻的值。

| | 主机 RAM | 主机 Flash | 从机 RAM | 从机 Flash |
|---|---|---|---|---|
| 卡住时 | **dd28** ❌ | a2a2 ✅ | a2a2 ✅ | a2a2 ✅ |
| 重启主机后 | a2a2 ✅（从 Flash 读回） | a2a2 | a2a2 | a2a2 |

→ 匹配上 → 回连成功。**这也解释了"重启从机没用"**：分歧只存在于主机的 RAM 里，从机自始至终自洽
（§三.2 说"从机侧没问题"是对的，脏的是主机那个只有 RAM 知道的提议值）。

> 可验证预测：重启主机时日志应打印 `load serverData = a2a2`。

### 4. 为什么这是必然复现而不是偶发

- **毒化只需一包**：主机只要收到**一次** `BOUND_REQ`（哪怕 RSSI −79 单包侥幸穿过），身份就被改写 → 永久卡死；
- **而真正连上需要一整条链**：RSP 过去 → 从机切参数 → 从机在新参数上发出第一包 → `rfBoundConfirm()`；
- 从机未绑定状态是**高速广播**的（日志里 `rej` 每秒 1800~2000 次），所以只要走过"刚刚能听见"那个
  距离带，**毒化几乎必然发生**，而完整握手成功要碰运气。

→ "一包进 = 永久中毒；一整条链成 = 才算连上"，这个不对称就是它稳定复现的原因。

### 5. ★ 第一次修复是错的（留档教训），正解是"回连时绝不改身份"

> 这一节请**连着读完**：先记下走错的那一步，否则很容易再踩一遍。

#### 5.1 第一版（已废弃）：只"提议"、成功才"提交"

思路是"主机别急着改 `gServerData`，等 `rfBoundConfirm()` 确认了再提交"：
新增 `gServerDataNext`，接受分支只写提议值，`rfBoundConfirm()` 里再 `gServerData = gServerDataNext`。

**结果：台架实测仍然连不上。** 看日志就明白了 —— 分歧没被消除，只是**换了另一侧**：

| 失败方向 | 日志 | 谁是新值 |
|---|---|---|
| 原代码：本机立即改身份，RSP 丢了 | `local dd28 remote a2a2` | **主机**是新值 |
| 第一版：主机不提交，但**从机收到 RSP 就落盘** | `local 38c2 remote 9927` | **从机**是新值 |

从机是"收到 `BOUND_RSP` 立刻 `rfSaveServerData()`"的，所以只要 RSP 送达而主机的
`rfBoundConfirm()` 没跑到（confirm 那一包丢了），从机就单方面升到了新值。

**结论（关键教训）**：只要"绑定身份还会变"，而变更又依赖一条**可能丢包的单向握手**，
两侧就一定有机会分歧 —— **不管你在哪一侧延迟提交**。延迟提交只是把分歧从一端搬到另一端。

#### 5.2 正解（FIX2，已实现）：回连路径上**一个字都不改身份**

只在**首次配对**（从机 `severData == 0`，走 RSSI 贴近分支）时才生成新身份；
**回连（`severData == gServerData`，身份已匹配）时 `gServerData` 保持不变**。

```c
BOOL reg=0;
uint8_t firstPair = 0;                       /* 1 = 首次配对：本次才生成新身份 */
...
if( pReq_t->severData ) { if( pReq_t->severData == gServerData ) reg = 1; }   /* 回连：身份不动 */
else                    { if( rssi > -58 ) { reg = 1; firstPair = 1; } }      /* 首次配对 */
if( reg )
{
    if( firstPair ) { gServerData = rf_rand16( rssi ); }   /* ← 只有这里会改身份 */
    ...
    pRsp_t->accessaddr = rf_rand_aa( gServerData );
    pRsp_t->severData  = gServerData;                      /* 回连时 = 旧值，两侧恒等 */
}
```

**为什么这样就证明不会分歧**：主机只接受 `severData == gServerData` 的请求，回的 RSP 里
`severData` 还是 `gServerData` → 从机 `gServerData = rsp->severData` 赋值前后**相等**。
因此无论 RSP 丢没丢、`rfBoundConfirm()` 跑没跑到，**两侧永远是同一个值**；一次失败只是重试。
首次配对那条路也没有永久分歧：RSP 丢了从机仍上报 0，永远走 RSSI 分支重新配对。

**代价**：回连沿用原 `accessaddr`/频点（`rf_rand_aa()` 是 `gServerData` 的纯函数：
`(rand<<8)|0x6E0000B6`），不再每次轮换 —— 对"回连"本就该稳定，反而更可预期。

**安全性不变**：身份不匹配的陌生主机/从机照旧被拒，严格绑定语义未动。

## 八、从机是否需要同步修改 —— 评估结论：**不需要**

### 1. 结论与证明

从机**没有**"无条件换身份"的写法，它只有一句被动赋值：
`rf_bound()` 里的 `gServerData = rsp->severData;`。而 FIX2 之后主机在**回连时回的还是同一个值**：

| 情形 | 主机 | 从机 | 是否一致 |
|---|---|---|---|
| RSP 送达 | `gServerData` 未动 = V | `gServerData = rsp->severData` = V | ✅ 恒等 |
| RSP 丢了 | V（未动） | V（没收到，未动） | ✅ 恒等 |
| `rfBoundConfirm()` 没跑到 | V（未动） | V（已落盘，值本身 = V） | ✅ 恒等 |

分歧的根因是"**身份值会变**"，FIX2 让回连路径上的身份**恒等**；从机只是被动赋值，
赋值前后相等 ⇒ 无论丢包与否两侧都是同一个值。**FIX2 单独即完备，从机不用改。**

### 2. 残留窗口：首次配对（低概率，**建议先不动**）

首次配对时主机**仍会**生成新身份 V′（这条必须保留）。若 **RSP 送达（从机已落盘 V′）→
confirm 丢了 → 主机在恢复前重启**，则主机 Flash 仍为 0、从机为 V′ → 永久拒。

- **概率低**：`rfBoundConfirm()` 只要收到从机**在 10 ms 轮询周期里的任意一包**即触发，
  此时主机正听在正确的参数上，需要连续全丢才可能；
- **要彻底关掉只能从机做对称修改**：新值先放 RAM、首次成功收发后再落盘、失败回退旧值。
  **不能**在主机上恢复 `!gServerData ||` —— 那等于重新打开"任意新主机接走已绑定从机"，
  与 README「严格绑定」的承诺冲突；
- **暂不做**：该路径当前工作正常，而从机 RAM 只剩 760 B（§六.2）。**先验证 FIX2。**

### 3. 后续建议：回连时的冗余 Flash 擦写（两端都有）

| 端 | 位置 | 行为 |
|---|---|---|
| 从机 | `rf_bound()` | **无条件** `rfSaveBoundInfo()` → 每次回连擦+写 4 KB 扇区 |
| 主机 | `rfBoundConfirm()` | 每次建链都 `rfSaveServerData()`（同样是擦+写） |

FIX2 之后回连时**值根本没变**，这次擦写纯属冗余。CH5xx Flash 擦写次数有限，
而链路临界时（现场日志里 `crc` 一直有）回连可能频繁，会累积磨损。

**建议**：值未变化就跳过写。⚠️ 从机那条记录还带 `bootCount` / `resv` / `dtrPol`，
**不能**一刀切按 `serverData` 判等。**本轮未改**，留作后续优化。

## 九、第二轮实测（fix3：RSSI 标定版）与"重连 RSSI 门限"的设计

### 1. 第二轮暴露的事实：**烧进去的不是 fix2**

用日志对照实验判定（不是猜）：

| 检索项 | 命中 | 说明 |
|---|---|---|
| `CH57x_RF_BASIC_LIB_V1.1.4`（对照：每次开机一行） | **5** | 5 次开机**全部**被记录 |
| `bound rsp sent`（对照） | 44 | 检索链路正常 |
| **`build:`（fix2 标识）** | **0** | 一次都没有 |

5 次开机时刻：`15:27:20 / 15:43:00 / 15:48:01 / 15:48:03 / 15:48:06`，**全部 ≤15:48:06**，
且此后**再没开过机**。反查 fix2 的 hex（解码回二进制）确认标识**确实在里面**、
`RF_UartRxInit` 反汇编也确认真的调了两次打印 —— 因此"日志里没有"是有效证据。

> **教训（已固化为流程）**：以后**烧完先确认 `build:` 行**再开测，否则整轮白跑。
> fix3 起标识里带了版本号，专门用来做这件事。

**但有个对结论有利的发现**：正在跑的固件在回连时**身份恒定** ——
`bound rsp sent.**6E39DAB6**` 出现 **44 次、值一次没变**。老代码与 fix1 的接受分支都会推进
`rf_rand16()`（有状态 LCG：`static holdrand`，每次调用都变），**只有"回连不改身份"才是恒定**。
且重配之后再没出现过 `rej … local X remote Y`（X≠Y）→ **"永久 reject"在现场已经不存在了。**

### 2. 抖动 = 临界距离，属预期现象

```
15:50:18–35  crc 81 → 234/s 攀升
15:50:35.446 connect timeout. → disconnect. → bound rsp sent → [bound success]   反复
15:51:30.716 起恢复稳定
```
`connect → ~1.3 s → connect timeout → disconnect → 立刻重连`，0.2~1.3 s 一轮。
机制：建链后 `gTimeoutMax = BOUND_EST_COUNT`，临界距离下丢包把 `gTimeout` 顶过阈值
→ 主机主动判超时拆链。**这是"临界距离"的正常表现，不是新 bug。**

### 3. ⚠️ 为什么"设计一个重连 RSSI 值"不够

1. **单阈值只能把抖动点搬走，不能消除抖动**：在阈值边界上会变成
   "接近→允许→立刻掉→拒绝→又允许" 的新抖动。要消除必须**双门限滞回**：
   `R_JOIN`（准入，较严）> `R_KEEP`（保持，较松），中间那段是"已连上就不折腾"的滞回带。
2. **绝不能复用首配的 `-58 dBm`**：那个值是故意严的（"贴近配对"用来人工指定连哪一台）。
   若回连也用它，`-65 dBm` 这种**完全可用**的链路会被拒 —— 恰恰破坏刚修好的回连。
   两个门限**语义不同**：首配是"选哪台"，回连是"够不够稳"。
3. **原来缺数据**：RSSI 此前**只在 `rej` 行**打印，成功建链/回连时从不打印
   → 没人知道抖动发生在多少 dBm，拍出来的阈值没有依据。

好消息：**决策点上本来就有 RSSI** —— `rf_uart_rx.c:479` 在收到 `BOUND_REQ` 时就读取了它
（偏移 `pPkt->length + 2 + 2`），加门限**不需要新管线**。

### 4. fix3 做了什么（**只加观测，行为零变化**）

对全部代码改动做了逐行核对（剔除注释后 diff），非注释改动**只有三类**：

| 类别 | 内容 |
|---|---|
| fix2 的修复（本轮沿用） | `firstPair` 声明 / 首次配对置位 / `if( firstPair )` 守卫 |
| **纯赋值**（ISR 内，不判断不打印） | 接受路径记 `gJoinRssi`；连接态逐包记 `gRxRssiLast/Min/Cnt` |
| **纯打印**（只在主循环 `rfDiagReport()`） | `join rssi %d` / `rx rssi %d min %d n %u` |

**没有任何控制流变化**：唯一的 `if` 只包住打印与最小值统计，不参与协议判断。
打印一律放主循环 —— ISR 里 PRINT 会把主机拖垮（已有前车之鉴）。

新增两条日志：
```
join rssi -63             ← 接受一次建链/回连时的 RSSI  → 标定 R_JOIN
rx rssi -58 min -71 n 97  ← 该秒内最近/最差/采样包数     → 标定 R_KEEP
```

## 十、★ 连续灌数据标定 → fix4：回连 RSSI 质量门限（已实现）

### 1. 标定方法与实测曲线

空闲轮询下 `n` 掉一点不致命，**灌数据时丢的才是数据**。所以本轮用**连续发送 + `crc` 计数**标定，
判据取 **丢包率 = `crc / n`**（比绝对 `crc` 准：不同距离下 `n` 本身在变）。

| `rx rssi` | `min` | `n` | `crc`/s | **丢包率** | 判定 |
|---|---|---|---|---|---|
| −24 … −40 | −26 … −42 | 1050 – 1100 | 1 – 29 | **0.3 – 3%** | ✅ 正常 |
| −41 … −48 | −42 … −68 | 1022 – 1089 | 53 – 77 | **5 – 7.5%** | ⚠️ 开始退化 |
| −51 … −57 | −58 … −75 | 711 – 1085 | 109 – 175 | **10 – 24%** | ❌ 明显退化 |
| −62 … −70 | −71 … −83 | 640 – 990 | 109 – 204 | **12 – 30%** | ❌ 差 |
| −72 … −76 | −77 … −82 | 150 – 830 | 150 – 324 | **23 – 80%** | ❌ 很差 |
| −79 … −84 | −81 … −84 | **11 – 388** | 20 – 185 | 崩塌 | ❌ 死（`n` 归 1）|

**门限对照表**

| 目标丢包率 | 需要的 RSSI |
|---|---|
| ≤ 3% | −40 dBm |
| ≤ 5% | −45 dBm |
| **≤ 10%** | **≈ −52 dBm** ← 本轮采纳 |
| ≤ 20% | ≈ −60 dBm |
| ≤ 30% | ≈ −68 dBm |
| 崩溃（`n` 塌） | ≤ −73 dBm |

**两个必须记住的点**

1. **有不可避免的干扰底噪**：即使 −30/−40 也出现过 `crc` 29~65/s（**3~6%**）突发 —— 2.4G 环境本身的干扰。
   **不要指望 `crc = 0`**，门限只能定在"某个可接受丢包率"上。
2. **`min` 比"最近值"更能预测丢包率**（深衰落才是丢包的来源）：
   `-39/-40`→0.7%、`-51/-58`→5%、`-54/-63`→15%、`-57/-73`→24%、`-76/-78`→65%。
   → 判据要用滤波值或一秒内最差值，**不能拿单次瞬时读数**。

### 2. fix4 的设计（采纳 10% → `R_JOIN = −52 dBm`）

只改**回连的准入条件**。原来只要"绑定身份对得上"就接受，现在要三条同时满足：

| # | 条件 | 作用 |
|---|---|---|
| ① | 身份与本机记录完全一致 | 严格绑定（原有，安全语义不变）|
| ② | **连续 `JOIN_GOOD_N = 3` 次**广播的 RSSI 都 **≥ `RSSI_JOIN_MIN = −52`** | 滤掉深衰落"刚好飘上来一下"的毛刺 |
| ③ | 不在**掉链冷却**期内（`JOIN_COOLDOWN_MS = 1000`）| 即使信号在门限附近飘，也不会每几百毫秒连断一次 |

**效果**：−73 以下那种"接上 300 ms 就掉"会被**直接拒绝**，链路停在"未连接"（LED 快闪），
而不是每 300 ms 连断一次（PC 端 USB 也不会再反复枚举）。

**为什么不需要"保持侧"门限**：链路恶化到撑不住时会自然超时断开；断开后按②③就再也接不回来，
直到用户走进 −52 以内。**滞回天然由"准入严格"实现**，不必再判 RSSI 去主动拆链。

### 3. ⚠️ 首配那道 −58 门限**没有动**（有意）

`rssi > -58` 是**首次配对**的门限，语义是"贴近"（人工指定连哪一台），而且比 −52 松。
所以可能出现**"配得上、但回连不上"** —— 这是**有意**的：那种位置本来就跑不动数据，
让用户走近一点比假装连上更诚实。**不要**为了"一致"把首配也改成 −52：代码注释里记着
本对板近距离实测有到 −56 的情况，改严了可能**永远配不上**。

### 4. 日志判读（新增）

| 日志 | 含义 |
|---|---|
| `rej N local X remote Y rssi Z`，**X == Y** | 被**信号质量门限**拒（身份匹配，只是信号差）|

| `rx rssi -58 min -71 n 97` | 连接态：最近一包 / 最差包 / 采样包数 |

## 十二、★ fix5/fix6 台架验证 + **保持侧参数的最终取舍**（定稿）

### 1. fix5（保持侧 10%）功能正确，但**代价不可接受**

保持侧按设计工作 —— 三次实测断点（都是 `crc/n > 10%` 连续 3 秒触发）：

| 断开时刻 | 触发值 | 断开瞬间 RSSI |
|---|---|---|
| 16:43:56.749 | `crc 190/951` = 20.0% | ≈ **−62** |
| 16:45:08.805 | `crc 198/1081` = 18.3% | ≈ **−75** |
| 16:46:07.938 | `crc 145/963` = 15.1% | （该段日志已回收）|

**问题**：fix4（无保持侧）时链路会一路撑到 **−83**；取 10% 后断点前移到 **−62 ~ −75** ——
"能跑但慢"的那一大段可用距离被砍掉了。台架反馈：**断开距离明显变近，不可接受。**

> **教训**：`10%` 这条线是**准入**该用的（"连上就必须能用"）；
> 把它同时当作**保持**门槛（"稍差就断"）是**过度收紧** —— 两者语义不同：
> 准入决定"要不要建立"，保持决定"要不要放弃"。**放弃的门槛必须比建立的门槛松得多。**

### 2. fix6（定稿）：准入严格 + 保持宽松

**只改一个常量**：`LINK_QUAL_MAX_PCT` **10 → 40**。其余一字未动。

| 参数 | 值 | 语义 |
|---|---|---|

| `LINK_QUAL_BAD_SECS` | 3 | 连续超标秒数（防抖）|

### 3. 最终行为（定稿语义）

- **准入严格**：连上就意味着"能用"（信号 ≥ −52，≈10% 丢包线以内）；
- **保持宽松**：连上后不因为"稍差"就断，只在链路真的坏了（>40% 连续 3 秒）才断，
  否则交给自然超时；
- **断开后不抖**：准入门限 + 1 s 冷却挡住所有重连，链路停在"未连接"（LED 快闪）；
- **走回自动回连**：进到 −52 以内干净地回连一次。

   M 只有 15~20% 就断 = `LINK_QUAL_MAX_PCT=10`（fix5）；要到 >40% 才断 = 40（fix6）。

| 6 | Flash 擦写期间 `SYS_DisableAllIrq/RecoverIrq` | 从机 | 见 §2 —— **推测**擦写期间射频 ISR 取指失败会破坏状态 | ❌ **未解决问题：加了之后现象依旧** |
| 7 | 收到极性指令后**保存并自行软复位**（`SYS_ResetExecute`）| 从机 | 权宜解：现场"切完极性 LED 异常、环卡死、只能手动重启" | ✅ 手动重启能恢复的都被它替代 |
| 8 | 保存极性时 `bootCount = 0` | 从机 | ★ 主动重启会计入"连续重启 5 次解绑"→ **不处理的话连改 5 次极性就会解绑设备** | ✅ 连改多次不解绑 |
| 9 | `BOOT_FAST_RESET_SEC` 15 → **5** | 从机 | 判定窗口越短，"普通断电再上电"越难被误判成快速重启 | ✅ |
| 10 | 极性保存从**主循环**移到**射频 ISR**里立刻做 | 从机 | 见 §2：主循环那条路会先陷入约 6 秒失步风暴 | ⏳ 待现场确认 |

### 2. ★★ 未结问题：切极性指令会引发约 6 秒的序号失步重传风暴，且从机 LED 异常 ★★

**这是留给下一位工程师的主线问题。目前的"自重启"只是让现象消失，根因未定。**

#### 现象（实测日志，2026-10-15 18:12）

```
[18:12:43.534] dtr pol cmd:1          ← 主机认出魔数并下发 OPCODE_DTR_POL
[18:12:44.226] crc 15 ... dup 1588 rtx 1476 usb 4     ← 0.7 秒后开始失步
[18:12:45.224] dup 3119 rtx 3119 n 3124               ← 满速重传风暴
[18:12:49.226] dup 3194 rtx 3194 n 3202               ← 持续约 6 秒
[18:12:50.225] giveup 1                               ← 破活锁围栏触发
[18:12:50.984] connect timeout. / disconnect.         ← 从机此刻才重启（晚了 6.5 秒）
[18:12:53.159] bound success (link up).               ← 2 秒后回连
```

两个伴生现象：
- **从机 LED 异常**（"亮一段时间" / 恒亮），只有重启从机能恢复；
- **下发延迟**：极性/重启要排在风暴之后，实测约 6.5 秒。

#### 已排除的假设（都有证据，别再走一遍）

| 假设 | 排除依据 |
|---|---|
| 魔数字节序写反 | 主机日志明确打出 `dtr pol cmd:1/0`，说明魔数被正确识别 |
| 从机"没识别串口数据 vs 厂商指令" | 识别在**主机**做（`usb_uart.c` 的 `dtrPolMagicFilter`）；从机按 **opcode**（`OPCODE_DATA=0x00` / `OPCODE_DTR_POL=0x02`）分发，**全工程没有任何魔数处理** |
| 程序跑飞 | 主循环若停摆，主机 `CONN_TIMEOUT`(100×10ms) **1 秒内**必判超时；实测风暴期间持续有包 |
| RX 悬空拾噪 | `GPIOA_ModeCfg(RXD_PIN, GPIO_ModeIN_PU)` 已配内部上拉 |
| 切主频后 LED 时基过期 | `rfApplyLineCode()` 在 `GetSysClock() != clkBefore` 时**会重新标定** `LedTimerCalibBegin/End` |
| `rfDelayMs` 死循环 | 有 `gLedTicksPerMs == 0` 兜底 |
| 帧错误（波特率不匹配）造成假数据 | `UART_II_LINE_STAT` 分支只读状态清中断，不动任何标志 |
| 从机发送环没被创建 | `RF_UartTxInit()` 里有 `rf_buffer_create(&pRfBuf)` |
| LED 与 DTR 引脚冲突 | LED=PA7、DTR=PA3、RTS=PA2，不冲突 |
| `write_buf()` 返回值语义用错导致环不排空 | 环满时它返回 `buf->data_len`（占用数，非 0），`if(gRfRxFlag)` 门是开的 |
| `read_buf()` 整包拒收导致死锁 | 它允许部分读（`data_len < *len` 时自动夹小） |
| `R8_UART_TFC` 语义反了 | SFR 注释明确是"transmitter FIFO **count**"，空时为 0 |
| TX 中断被关掉 | 全工程只有 `UART_Init()` 里 `UART_INTCfg(ENABLE, ... RB_IER_THR_EMPTY)` 一次，再无 DISABLE；`UART_SetBuad()` 只写 `R16_UART_DL` |
| Flash 擦写期间射频 ISR 取指失败（推测）| **加了 `SYS_DisableAllIrq/RecoverIrq` 后现象依旧** —— 此假设不成立 |

#### 建议的下一步取证

从机没有可用日志通道（`PRINT` 走 PA0/PA1，正是数据口；且默认不开 `-DDEBUG`）。要定位必须从从机侧取数，两条路：

1. **计数捎带上来（推荐）**：把"UART 发送环占用 / 读指针 / `R8_UART_TFC` / TX 中断进过几次 / `gTxDataSeq` / `rfProcessRx` 走的是哪个分支"塞进状态应答的保留字节，主机打印。**"中断在进但环不降"与"中断根本不进"是完全不同的两个病，只有这个能区分。**
2. **临时开从机 `-DDEBUG` + 用 USB-TTL 读 PA0**：代价是 RAM 到 96%+（偏危险），且日志占用数据口（测试时目标口空着可接受）。

#### 复现步骤

1. 主机烧 `RF_UartDongle_FIX7-DTR可靠.hex`，从机烧 `RF_Uart_dtrREBOOT.hex`
2. 贴近连上，确认主机日志在刷 `rx rssi`
3. 主机数据口发 `A5 5A 01 01`（HEX、无行尾、单次 4 字节）
4. 观察主机日志：`dtr pol cmd:1` 之后是否出现 `dup/rtx` 飙到 ~3000/s 的风暴；从机 LED 是否异常

### 4. 一个跨版本的方法论坑（务必遵守）

**烧录会让 MCU 复位 → USB 重新枚举 → 串口面板重开，开机那几行（含 `build:`）很可能就在这一瞬间丢掉。** 实测踩过：日志里 `build` 还是上一次的版本号，而新版本独有的字符串确实打出来了。

- 主机有 `build:` 标识（`RF_FW_TAG`），但**别只看它** —— 烧完最好手动断电再上电一次专盯开机块；
- **从机默认不开 `DEBUG`、没有任何开机打印**，只能**用 MD5 认版本**。
